# WARP.md

This file provides guidance to WARP (warp.dev) when working with code in this repository.

## Overview

Easy Stock is a small full-stack app for warehouse/inventory management:
- **Backend**: Node.js + Express REST API, backed by **PostgreSQL** via **Prisma ORM**.
- **Frontend**: Single-page dashboard written in **vanilla JS**, rendered from `index.html` and `app.js` without a bundler.
- **Database**: Prisma schema in `prisma/schema.prisma` with migrations in `prisma/migrations/`.
- **UX**: Perplexity-inspired design system in `style.css`, light/dark theme toggle, voice control, and an edit-mode flow with staged changes.

The server serves static assets from the project root and exposes CRUD endpoints that the dashboard consumes.

## Environment & Setup

From the root of the repo:

- **Install dependencies** (Node 18+):
  - `npm install`

- **Configure environment** (PostgreSQL 15+):
  - Copy and edit env file as per `README.md` (expects `DATABASE_URL` used by Prisma).

- **Run database migrations** (uses `prisma.config.ts` + `prisma/schema.prisma`):
  - Apply latest migrations: `npx prisma migrate dev`
  - (Optional) Seed DB if/when a seed script is added: `npx prisma db seed`

- **Start the server** (serves API + static dashboard):
  - Development / run: `npm start`
  - `npm run dev` currently aliases `npm start`.

There is **no test or lint script configured** in `package.json` yet. Before adding tests or tooling, wire them into `package.json` scripts so they can be invoked consistently (for example `npm test`, `npm run lint`).

## Backend Architecture (Express + Prisma)

Key files:
- `server.js` — Express app + REST API + Prisma wiring.
- `prisma/schema.prisma` — database models and relations.
- `prisma.config.ts` — Prisma CLI configuration (schema path, migrations path, `DATABASE_URL`).
- `prisma/migrations/*` — SQL migrations generated by Prisma.

### Server responsibilities (`server.js`)

- Creates an `express()` app with JSON parsing and `express.static(__dirname)` so all root files (`index.html`, `app.js`, `style.css`, etc.) are served directly.
- Instantiates a single `PrismaClient` and disconnects it on `SIGINT`.
- Adds a simple **UUID param validator** middleware (`validateUUID`) used on routes with `:id`.
- Normalizes invoice statuses via `normalizeInvoiceStatus` (maps localized strings like `pendiente`, `vencida` to canonical values like `PENDING`, `OVERDUE`).
- Central product payload validator/normalizer: `buildProductUpdateData(payload, currentProduct)`:
  - Validates required fields (`name`, `sku`, etc.).
  - Ensures numeric fields are non-negative integers.
  - Validates `unitPrice` and `expirationDate`.
  - Enforces `minStock <= maxStock`.
  - Throws a custom `ValidationError` with a list of localized error messages used by the API.

### REST API surface

All routes are mounted on the same Express app and use Prisma directly:

- **Products**
  - `GET /api/products` — returns all non-deleted products (`deletedAt: null`), ordered by `name`.
  - `POST /api/products` — creates a new product from the raw body (no `buildProductUpdateData` here yet).
  - `PUT /api/products/:id` — validates UUID, checks soft-deletion, runs `buildProductUpdateData`, then updates the product.
  - `DELETE /api/products/:id` — soft-deletes a product by setting `deletedAt`.
  - `PUT /api/products/:id/stock` — atomic stock adjustment:
    - Validates `cantidad` and `tipo` (`entrada`/`salida`).
    - Uses a Prisma transaction to update `currentStock` and insert a `StockMovement` row (with before/after quantities, reference/notes).

- **Alerts**
  - `GET /api/alerts` — unresolved alerts (`resolved: false`), including related `product`.

- **KPIs / dashboard**
  - `GET /api/kpis` — aggregates over `Product` + `Alert` + `WarehouseConfig`:
    - Calculates `totalProducts` (sum of `currentStock`), `totalValue`, critical-stock count, unresolved alert count.
    - Loads `WarehouseConfig` to derive `totalCapacity` and `occupiedPercentage` (caps at 100%).

- **Invoices**
  - `GET /api/invoices` — upcoming invoices between today and 7 days ahead, filtered to non-deleted ones. Statuses normalized and filtered to a subset (`PENDING`, `OVERDUE`) before returning.
  - `DELETE /api/invoices/:id` — soft-delete via `deletedAt`; 404 if already deleted.

- **Tasks**
  - `GET /api/tasks` — tasks ordered by `createdAt`.
  - `DELETE /api/tasks/:id` — deletes a task; translates Prisma `P2025` into 404.

- **HTML entrypoint**
  - `GET /` — serves `index.html` from the project root.

Error-handling is intentionally simple: API routes log server errors to stdout and return generic JSON error messages, with special cases for validation errors and unique-constraint conflicts.

### Data model (Prisma)

`prisma/schema.prisma` defines the main entities. High-level mapping:

- **WarehouseConfig** (`warehouse_config`)
  - Singleton configuration row (id=1) with global capacity, units of measure, expiry thresholds, etc.
  - Used in `GET /api/kpis` to parameterize capacity-related KPIs.

- **Zone** (`zones`)
  - Warehouse zones with capacity and type metadata; not yet fully surfaced in the UI but designed for future zoning logic.

- **Product** (`products`)
  - Core stock entity: `sku`, `name`, `category`, `barcode`, `currentStock`, `minStock`, `maxStock`, `unitPrice`, `currency`, `location`, `zone`, `numberOfUnits`, `expirationDate`, `supplier`, `deletedAt`, timestamps.
  - Indexed for performance (category, location, expiration, stock levels, soft delete) and has a trigram index on `name` for fuzzy search.
  - Relations: `alerts` (Alert[]), `stockMovements` (StockMovement[]).

- **StockMovement** (`stock_movements`)
  - Tracks every stock adjustment with before/after quantities, reference, optional cost details, timestamps, and creator.
  - Linked to `Product` via `productId` with cascade-on-delete.

- **Alert** (`alerts`)
  - Event-like records: `alertType`, `category`, `title`, `message`, `resolved`, `autoGenerated`, timestamps, optional `productId`.
  - Used both for API-served alerts and potential future non-product alerts.

- **Invoice** (`invoices`)
  - Supplier invoices: `invoiceNumber`, `supplierName`, `subtotal`, `taxAmount`, `totalAmount`, `currency`, issue/due/paid dates, `status`, payment metadata, file path, notes, soft-delete (`deletedAt`).

- **Task** (`tasks`)
  - Operational tasks with `title`, `priority`, `assignedTo`, `supervisor`, `phone`, `status`, `dueDate`, `notes`, timestamps.

When updating schema:
- Add/change fields in `schema.prisma`.
- Run `npx prisma migrate dev` to create/apply migrations.
- Regenerate the client (`npx prisma generate` if needed) and keep `server.js` + frontend normalizers in sync.

## Frontend Architecture (Dashboard SPA)

Key files:
- `index.html` — markup for the dashboard layout, error banner, modal dialogs (edit confirm + product editor), voice button, theme toggle.
- `app.js` — main SPA logic: data fetching, normalization, local state, offline caching, edit mode, product editor, voice control, calculations for KPIs, warehouse health, and occupancy.
- `style.css` — design system (CSS custom properties for tokens, light/dark themes via `data-color-scheme`), layout, cards, tables, modals, floating buttons.

### Data flow and state (`app.js`)

- Global state object `appState` holds:
  - `products`, `invoices`, `tasks`, `alerts`, `warehouseConfig`, `kpis`, and `errorMessage`.
- On `DOMContentLoaded`, `init()` runs:
  - Calls `loadData()` (parallel `fetch` to `/api/products`, `/api/alerts`, `/api/invoices`, `/api/kpis`, `/api/tasks`).
  - Normalizes API responses into UI-friendly structures (Spanish field names, dates, etc.).
  - Generates **derived alerts** (stock and expiration based) in addition to alerts from the API.
  - Computes KPIs locally and updates the DOM.
  - Sets up event handlers for edit mode, deletion, product editor modal, voice control, connectivity listeners, etc.

### Normalization and mapping

The frontend is intentionally tolerant of backend evolution; several helpers map DB/API fields to UI fields:

- `normalizeProduct(product)` — maps Prisma `Product` fields (`name`, `sku`, `currentStock`, `unitPrice`, `category`, `expirationDate`, `location`, `zone`, etc.) into Spanish UI fields like `nombre`, `stock_actual`, `precio_unitario`, `caducidad`, `zona`, `ubicacion`, and `stockMin/stockMax`.
- `normalizeAlert(alert)` — maps backend `Alert` into UI alerts with `title`, `description`, `priority`, `type`, merging server-provided messages with contextual product info.
- `normalizeInvoice(invoice)` + `mapInvoicesForState()` — unify invoice shape (IDs, amount, due date, status) and attach stable `_uiId` identifiers used by edit mode.
- `mapTasksForState()` — adds `_uiId` to tasks for UI-level identity.

When changing backend fields or adding columns:
- Ensure the corresponding `normalize*` functions still produce valid UI fields.
- Keep Spanish-label logic (e.g., localized strings in error messages and labels) consistent.

### Dashboard widgets

- **KPIs**:
  - `updateKPIs()` computes totals from `appState.products` and `appState.alerts` and fills DOM nodes `#kpi-total-products`, `#kpi-total-value`, `#kpi-alerts`.
- **Alerts panel**:
  - `renderAlerts()` lists `appState.alerts` with severity-specific styling.
  - Alerts include both API and auto-generated ones, sorted by priority.
- **Products table**:
  - `renderProductsTable()` renders rows using `appState.products` and marks rows as `pending-edit` / `pending-delete` when edits are staged.
  - Uses `getDaysUntilExpiration()` to annotate `caducidad` with critical/warning badges.
- **Warehouse health / occupancy**:
  - `calculateWarehouseHealth()` derives a 0–100 score from alert counts, occupancy, and excess-stock counts.
  - `updateWarehouseGauge()` updates the SVG gauge and card styling based on that score.
  - `updateSpaceOccupancy()` computes usage vs `warehouseConfig.capacity` and updates the progress bar.
- **Invoices & tasks lists**:
  - `renderInvoices()` and `renderTasks()` render cards with delete buttons that are only active in edit mode.

### Edit mode and staged changes

A notable architectural feature is the **two-phase edit flow**:

- `isEditMode` and `editSession` manage an editing session:
  - `editSession.snapshot` stores deep copies of `products`, `invoices`, `tasks` when entering edit mode.
  - `editSession.invoices`, `.tasks`, `.products` track staged deletions/updates.
- **Entering edit mode**:
  - `enterEditMode()` creates a snapshot and toggles `body.is-edit-mode` (affects styles, shows delete buttons, etc.).
- **Staging edits**:
  - Delete buttons for invoices/tasks call `stageItemForDeletion()` which updates `editSession` and re-renders lists.
  - Row-level product edits open the product editor modal, which gathers form values, validates them (`validateProductForm()`), and stages changes in `editSession.products` via `stageProductUpdate()` while previewing changes in the table.
- **Confirming / cancelling**:
  - On exit from edit mode, if there are pending changes, `openConfirmModal()` shows a summary modal.
  - `handleModalConfirm()` calls `applyPendingChangesToServer()` (which uses the REST API to apply deletes/updates) and then updates local state via `removePendingItemsFromState()`.
  - `handleModalCancel()` closes the modal and restores the pre-edit snapshot.

This design centralizes side effects and ensures the user sees a summary of all pending changes before applying them, and allows full rollback within a session.

### Offline mode and sync queue

The frontend includes optimistic offline support:

- Uses `localStorage` keys:
  - `easy_stock_cache_v1` — cached snapshot of `appState`.
  - `easy_stock_queue_v1` — queue of pending changes to sync when connection is restored.
- On startup, if the initial API load fails, it attempts to restore from cache and enters offline mode with a banner message.
- `pendingSyncQueue` holds entries with invoices/tasks/products to modify. `flushPendingQueue()` replay changes via API calls when `navigator.onLine` becomes true.
- `shouldEnqueueOffline(error)` detects network-like failures and enqueues changes instead of failing hard.

If you change API contracts or add new endpoints, be careful to:
- Update the offline queue format and `processQueuedEntry()` as needed.
- Keep local normalization consistent with server-side validation rules.

### Voice control and theming

- **Voice control** (`initVoiceControl()`):
  - Uses `window.SpeechRecognition || window.webkitSpeechRecognition` (if available) to listen for simple Spanish phrases and scrolls to relevant dashboard sections.
  - Button state is managed via `.listening` class and basic error handling.

- **Theme toggle** (inline script in `index.html`):
  - Uses `data-color-scheme="light" | "dark"` on `<html>` and persists choice in `localStorage` under `theme`.
  - `style.css` defines both light and dark token overrides for this attribute.

## Project-specific Notes

- `OPTIMIZATIONS.md` documents performance/accessibility/UX optimizations and lists some legacy files under `archive/` (and previously `styles.css`, additional JS helpers) that are not part of the current production path.
- `archive/` contains historical artifacts (e.g. `archive/react-app.jsx`, `archive/README_v1.md`) from an earlier React-based or pre-Prisma iteration. Treat these as reference; the live code path is `index.html` + `app.js` + `server.js` + Prisma.

When making structural changes, prioritize keeping:
- Prisma schema, migrations, and `server.js` API layer consistent.
- Frontend normalizers (`normalizeProduct`, `normalizeAlert`, `normalizeInvoice`, etc.) in sync with backend field names.
- Offline/edit-mode flows coherent so staged changes still behave correctly across connectivity transitions.
